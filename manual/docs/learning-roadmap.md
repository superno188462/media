# 从内卷树懒学会 DSH 插件与新项目开发

版本：`0.1.0-draft.1`；日期：2026-10-26。本文是教学与迁移计划，不构成已经实现的能力。

## 1. 先建立四个概念

| 概念 | 在本项目的例子 | 你需要能回答的问题 |
| --- | --- | --- |
| Harness | DSH 的 Agent 循环、会话、模型和工具生命周期 | 哪些能力已经有了，为什么不重写？ |
| Plugin | 内卷树懒草稿、审核、工作台与任务管理 | 插件何时加载、依赖什么、如何卸载？ |
| Skill | 选题规则、树懒文风、工具使用说明 | 规则在哪里结束，程序授权从哪里开始？ |
| MCP | 已有生图/素材能力，未来可独立复用的外部工具 | 工具输入输出、超时和副作用是什么？ |

一个 Skill 可以告诉模型“发布前需要审核”，但不能阻止模型调用另一条浏览器路径。授权必须落实到可执行边界。

## 2. 逐阶段学习与交付

| 阶段 | 学习重点 | 最小练习 | 产物与验收 |
| --- | --- | --- | --- |
| L0 读规格 | 需求、状态、Schema、可观察行为 | 手画“批准”和“超时”的两条路径 | 解释 REQ-06/09 与 BE-RULE-01/05 |
| L1 插件入门 | `apply`、依赖注入、配置与资源释放 | 在隔离 profile 注册一个只读问候工具 | 加载、调用、卸载均可验证，无平台写操作 |
| L2 契约骨架 | 类型、Port、错误边界、组合根 | 给 DraftService 写声明和假外部端口 | 可类型检查，业务体仍未实现 |
| L3 行为测试 | 测正常、边界、重复、并发和错误 | 测旧版本批准被拒绝 | 测试绑定 SDD，不 Mock 被测服务 |
| L4 垂直切片 | DSH 到应用服务到持久化 | 用假飞书/假抖音跑完一次审批 | 能重启恢复，未批准不派发任务 |
| L5 真平台适配 | SDK/浏览器、身份验证、回执与不确定性 | 真飞书回调＋抖音草稿，再做授权测试发布 | 分别记录真实证据；不把单测当集成 |
| L6 做第二个工具 | 复用与替换 | 把“树懒”换成另一人设，把投稿换为本地导出适配器 | 业务审核规则不改，换配置/适配器即可 |

L1 及以后需先通过相应阶段评审。教学示例置于隔离环境，不作为真实投稿权限。

## 3. 怎样阅读代码（实现阶段使用）

沿一条用例读：`DSH 工具注册 → Controller → Application Service → Domain Port → Adapter → 结构化结果`。每读一层，找对应的需求编号、输入、输出、错误和副作用。

对一次“通过并发布”，至少能解释：操作者身份来自哪里、版本如何绑定、重复回调如何返回、哪个动作可能对外发送、为何结果未知时不能重发。

## 4. 后续开发时的教学约定

- 每个小步说明“本次学习什么、为何放在这一层、如何验证”。
- 新公开类型/方法写 TSDoc；Python MCP 的公共方法写 docstring 和字段说明。
- 单次只填充一个已批准的业务函数，运行其相关契约测试后再继续。
- 出错时先定位违反了哪条契约，避免直接堆补丁。
- 不一次生成大批无法讲解的生产代码；但也不为教学另造一套与产品无关的复杂框架。

## 5. 将来做商业工具，哪些东西可以复用

| 本项目能力 | 可复用部分 | 新商业项目必须重新定义 |
| --- | --- | --- |
| DSH 宿主 | 工具/界面适配经验、运行配置方式 | 宿主版本、授权、部署和分发 |
| 草稿与审核 | 不可变版本、审核授权、过期和回调去重 | 客户角色、审批层级、业务风险和内容规则 |
| 异步任务 | 状态、恢复、结果未知处理、回执 | 新平台的提交语义和查询证据 |
| 平台适配 | Port 和可替换依赖结构 | 供应商 API、权限、条款、速率与费用 |
| 人设配置 | 人设与业务规则分开 | 新受众、价值主张、素材和商用授权 |
| MCP 工具 | 自描述 Schema、错误、长任务模式 | 谁能调用、服务如何计费和隔离 |

“套壳”提供的是产品界面和交付形态；可持续价值通常来自明确场景、可靠流程、数据与适配。换名称和提示词不自动解决客户权限、平台许可或服务稳定性。

## 6. 新项目启动的可复制步骤

1. 写一句可验证目标：“谁输入什么，得到什么可核对结果”。
2. 画一个完整用户流程，列出真实外部副作用。
3. 列 DSH 已有能力、候选插件、缺口与验证证据。
4. 写 PRD/UI，并确认范围和默认值。
5. 写 Schema、行为 SDD、状态、错误及验收矩阵。
6. 先做可导入骨架，再写契约测试，按函数实现。
7. 外部依赖先用假适配器；之后单独记录真平台验收。
8. 客户上线前补身份、租户、凭据、计费、备份、许可证与支持策略。

不要直接复制本项目的“24 小时审核”“1–9 张图”等产品默认值。可以复制问题清单和结构，具体规则必须由新项目定义。

## 7. 自测问题

- 如果用户在飞书批准 v2，DSH 已经写出 v3，应该发哪一份？为什么？
- 如果浏览器点击发布后崩溃，为何不能只看本地状态重新点击？
- 如果 MCP 工具存在，是否说明真实抖音上已经验证可用？
- 如果创建另一个内容角色，哪些代码应完全不改？
- 如果将来为两家公司运行，增加一个 `tenant_id` 是否足够？

能结合契约和测试回答这些问题，比记住某个 SDK 方法名更能支持你独立开发新项目。
