## GOV-04 变更流程

任何外部字段、枚举、签名、状态、错误、超时、授权、界面行为或数据保留承诺的改变，都先提出变更。新增兼容字段也需要同步消费者和测试；内部重构若行为不变则不改契约基线。

```text

原因与证据：
旧行为 → 新行为：
影响条款、生产方、消费方：
```

### CHANGE-002 视频内容支持（已实施）

> **状态：Schema 已修改，采用方案 A。** 2026-10-26 用户指示「先按第一步走吧，你先写契约文件」
> 后落地。实现范围**仅限契约**：SDD、审核卡片、发布适配器仍待补。

```text
编号：CHANGE-002
当前基线：Schema 0.1.0（候选，未锁定）；依赖 CHANGE-001（平台双枚举）
实施日期：2026-10-26

原因与证据：
  用户 2026-10-26 表示「后续可能会有视频」，并要求先写契约。
  原契约有两处硬阻断：content_type 为 const "image_text"；Asset 必填
  width/height 且无时长字段，是图片专用结构。
  平台侧能力存在：bili-cli 已支持视频投稿且默认携带「含AI生成内容」声明。
  实机证据：鲸鱼娘 Day 0（BV1pGnn67EC2）帧分析显示视频为程序化渲染，
  我们可用 ffmpeg + 逐帧渲染复现，故进入实现范围。

旧行为 → 新行为（已采用方案 A）：
  content_type: const "image_text" → enum ["image_text", "video"]
  Asset 新增可选字段：
    media_kind ∈ {image, video}，默认 image（缺省兼容既有图文）
    duration_ms: integer(1..600000) | null，视频必填
    frame_rate:  number(1..120)     | null，视频必填
  Asset.mime_type: enum 增加 video/mp4
  Asset.byte_size: 移除固定 10 MiB 上限，改为由 content_type 分支决定
  PublicationManifest 新增 allOf 两条分支：
    image_text → assets ≤9，media_kind 必须 image，mime 必须 image/*，
                 byte_size ≤10485760，duration_ms/frame_rate 必须 null
    video      → assets 恰好 1，media_kind 必须 video，mime 必须 video/mp4，
                 byte_size ≤104857600，duration_ms/frame_rate 必填

影响条款、生产方、消费方：
  - Schema：PublicationManifest.content_type / assets / allOf、Asset
  - ReadinessReport.capabilities：**尚未**增加视频能力项（待办）
  - 审核卡片：已实现「关键帧 + 时长/分辨率/体积 + 完整正文」，
    紫色「视频待审核」表头。
    关于完整视频：飞书卡片不能内嵌播放，但飞书 IM 支持 msg_type=media 的
    视频消息，客户端可直接播放。已实测通过（im/v1/files 上传 30 MB 上限，
    实测 1.6 MB 视频上传需把客户端超时调到 180 秒，默认值会 ReadTimeout）。
    因此改为「先发可播放的视频消息，再发审核卡片」，卡片注明
    「完整视频已作为上一条消息发出」。不需要外部 OSS。
  - 投稿适配器：按 content_type 分派（待办）
  - 内容摘要语义：视频必须用文件字节 sha256（BE-RULE-07），
    仅算 manifest JSON 摘要不足以证明字节未变

字段/签名/状态/错误差异：
  新增枚举值与三个 asset 字段。不改草稿/审核/发布任务状态机，不改错误码。

迁移、兼容性、回滚：
```

### CHANGE-003 视频视觉表现改造（已决定，阶段一未实现）

```text

当前基线：CHANGE-002 已实施的视频渲染管线（HTML + Playwright + ffmpeg）
决定日期：2026-10-26

原因与证据（实测，不是感觉）：
  用户 2026-10-26 指出「每次都是这个样式的面板，会让人失去看的兴趣」。
  对 test01.mp4 的实测统计：
    屏数            7 屏 / 约 36 秒
    版式种类        1 种（左卡片 + 右立绘 + 底字幕条，标题屏与片尾各 1 例外）
    立绘姿势        1 个，主体 5 屏完全重复
    转场            0 次（全部硬切）
    运镜            0（纯静帧）
  对照参考账号（BV1pGnn67EC2）虽同样使用固定版式，但有 5–6 种姿势与
  卡片状态的逐步递进，因此不显单调。
  结论：「固定版式」本身不致命；致命的是「固定版式 + 人物不动 + 画面不动」。

旧行为 → 新行为（分四阶段，本记录只锁定阶段一的范围）：

    名字到路径的映射，不需要改架构
  阶段四（未开始）：模板系统 —— 版式组合 + 配色 + 卡片样式 + 节奏，
    每条视频选一个模板，避免所有视频长一样

影响条款、生产方、消费方：
  - 生产侧：scripts/render_video.py、src/content/video/{template,compose,scenes}.py
  - 分镜数据：Scene 需支持 card_reveal（逐条出现的进度）与可选 motion 参数
  - **不改** manual/contracts/cyber-sloth.schema.json：分镜 JSON 属于
    生产侧的中间产物，不是对平台的发布契约。PublicationManifest 不变。
  - 审核侧：关键帧抽帧位置会随分镜拆分变化，条目数可能增加；
    卡片结构不变。

字段/签名/状态/错误差异：

迁移、兼容性、回滚：
  向后兼容：card_reveal 缺省时行为与现在一致（整卡一次出现）；
  motion 缺省时不做运镜。回滚只需停止使用新字段。

验证方式（阶段一完成后）：
```
